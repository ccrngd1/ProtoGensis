# Full-run cost estimate — from pilot `pilot_2026-10-22`

Generated by `python3 scripts/estimate_full_run.py pilot_2026-10-22`; the full
machine-readable table with per-row record provenance is
`results/pilot_2026-10-22/full_run_estimate.json`.

**This estimates COST ONLY, from measured pilot tokens. It makes no accuracy
projection: pilot accuracy (n=10) must not be extrapolated to the full run.**

## Method

- Full-set sizes from the committed data manifest
  (`ensemble_reboot/data/manifest.json`): gpqa = 198, math = 51, code = 61
  items; **3 seeds** per the acceptance criteria → scale = n_items × 3.
- Per-call token model: mean input/output tokens measured in the pilot per
  (model, effort, task set); the low/high range spans the 10th–90th
  percentile of measured output tokens (n=10 per cell; ranges are wide and
  honest about that).
- B per set (from stage0): gpqa = claude-opus-5-5, math = gpt-6-luna,
  code = gpt-6.1-sol.
- **effort-fallback** flag: that (model, effort) cell has no pilot
  measurement (stage2 hit the budget cap after 3 of 10 models), so tokens
  fall back to the same model's measured cells at other efforts. For those
  rows the effort axis is NOT informative — the stage2 sweep showed output
  tokens scale ~2–6× from low to max (e.g. fable-5-1 code: 744 → 13,510 mean
  output tokens), so fallback rows likely understate high-effort cost and
  overstate low-effort cost.
- A4 arms: panel = sol + grok-4.7 + kimi-k3 at the row's effort
  (`default` = each member at its own default level — the only combination
  the pilot measured) + one aggregator call at its default level (A4a =
  fable-5-1@high, A4b = haiku-5-5@medium). Aggregator tokens come from the
  measured stage1 aggregator records (mean input 2,072 tokens — problem +
  3 panel responses).

## Cost-matching solution (target: arms within ±15% per item)

From `full_run_estimate.json#cost_matching` (grid search over A1 effort,
A2 N∈[3,9] and effort, panel effort; A3 = 7 × B at default anchors the
target). **Result: cost-matching FAILS on all three sets** — residual
mismatch per arm vs the geometric center:

| set | best config found | per-item costs (a1/a2/a3/a4a/a4b) | residual per arm | within ±15%? |
|---|---|---|---|---|
| gpqa | A1@max, A2 = 5×@medium, panel@high | $0.094 / $0.110 / $0.153 / $0.215 / $0.168 | −33.9% / −23.1% / +7.6% / +51.3% / +17.7% | **NO** (max dev 51%) |
| math | A1@none, A2 = 3×@none, panel@high | $0.003 / $0.009 / $0.020 / $0.492 / $0.330 | −92.4% / −77.3% / −47.0% / +1221.5% / +785.1% | **NO** (max dev 12.2×) |
| code | A1@max, A2 = 9×@max, panel@xhigh | $0.010 / $0.091 / $0.071 / $0.460 / $0.335 | −85.2% / +33.5% / +3.9% / +574.0% / +391.4% | **NO** (max dev 5.7×) |

Why, and what to do:

- **gpqa** is close to matchable: A1/A2/A3 can be matched (A2 = 5×@medium is
  within −23%→+8% of A3), but the A4 panel (grok-4.7 + kimi-k3 are
  token-hungry: 14k/5k output tokens per gpqa item) can't come down because
  their swept-effort tokens were never measured — the panel effort knob is a
  fallback no-op in this search. Measuring panel members at `low` in a
  stage2 top-up would likely close the gap.
- **math and code are structurally unmatchable with the current B**: B is a
  cheap model (luna $0.10/$0.50, sol $2/$10 per 1M) while the A4 panel is
  priced 6–30× higher per token AND emits 10–20× more tokens. Even A2 with
  N=9 at max effort cannot reach the panel's cost. Options: (a) cost-match
  only A1/A2/A3 and report A4 at its natural cost with cost-per-correct as
  the comparison metric; (b) require B = cheapest model whose cost is within
  some factor of the panel; (c) shrink the panel's effort (needs the missing
  stage2 data) or swap grok-4.7 (the extreme token emitter) out.
- Math `a1_effort: none` / `a2_effort: none` in the search output is an
  artifact of fallback rows — all luna efforts cost the same under fallback,
  and `none` sorts first. Ignore the specific effort labels for math/code;
  the residuals are what matters.
